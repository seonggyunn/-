## 화면 변경

외부 브랜드는 한칸데이터, 내부 관리자 한칸 운영실 유지.
홈(/)은 동네 개인 식당/네이버 우선/받는 결과물/무료와 유료 차이를 먼저 보여준다.
/services는 인터뷰·비교3곳·원고1안·메뉴5개·사진10장·피드백1회·적용지원/재확인 범위를 명시한다.
/pricing는 무료0원과 유료 별도견적만 게시한다. 검증 전 165,000~220,000원/월220,000원은 내부 문서에만 있다.
/cases는 모든 자료가 가상임을 표시하고 관찰/고객확인/가설/적용예시/미확인을 분리한다.
/how-it-works, /faq, /contact는 권한·사실확인·운영자·직접지원·성과 경계를 정리한다.
/privacy, /terms는 실제 새 수집 항목과 목적·동의 선택/필수·보관·제공범위에 맞춰 수정했다. 법률 검토 완료 주장은 없다.
기존 URL 10개를 유지했다. 새 요금 결제·자동 수정·크롤링 서버·추가 CRM은 없다.

## 신청 호환성

`src/components/IntakeForm.tsx`로 접수 UI를 분리. 고객은 서비스 종류를 고르지 않는다.
필수: 상호, 지역/주소/지도 링크, 이메일, 고민(기본값 ‘잘 모르겠음’), 개인정보/회신 동의.
선택: 담당자/연락처/채널, 추가 내용, 자료 제공 가능, 신청 경로, 별도 마케팅 동의.
새 요청은 `request_version=restaurant-v2`, 기존 채널 배열은 `[naver]`, 업종은 음식점으로 분류한다. 다른 채널 주소는 참고 정보이며 해당 작업 구매를 의미하지 않는다.
지역/고민/자료/경로는 서버에서 검증 후 기존 `leads.notes`에 식별 가능한 형식으로 기록한다. 기존 관리자·DB·보고서 구조를 바꾸지 않는다. 내부 전문 서비스 분류가 필요하면 상담 후 관리한다.
담당자 생략은 빈 값으로 보관하고 관리자에는 ‘담당자 미입력’으로 표시한다. 익명 이름을 실제 이름처럼 생성하지 않는다.
기존 요청의 필드/채널 검증은 유지한다. 구형 요청은 담당자 필수, 새 요청은 매장 식별 필수·추가내용3000자 제한. 신청 지문에 정규화한 추가정보를 포함해 동명이인 매장/지역이 다른 신청을 중복 취급하지 않는다.
새 요청 동의는 `2026-10-30-restaurant-v2`, 구형은 기존 동의버전 유지. 기존 동의 이력은 수정하지 않는다.
접수 메일은 새 브랜드와 무료 최대3개/별도작업 경계를 안내한다. API는 수신 성공을 주장하지 않는다.

## 기존 기능 보존

DB 스키마/마이그레이션 변경 없음. 인증·조직 접근·승인/철회·작업 이력·메일 아웃박스/Reply-To·Supabase 비공개 파일 로직 유지.
신청 추가정보 표시를 위해 관리자 메모의 줄바꿈/미입력 담당자 표시만 개선했다.
고객용 PDF의 발행 브랜드만 한칸데이터로 맞추고 내부 상태·증빙 표시는 유지했다.
기존 관리자의 수동 기록으로 새 업무를 운영하며 비교매장 자동수집/통계 연동/편집툴이 구현된 것으로 표시하지 않는다.

## 수행한 검증

- `npm run typecheck`, `npm run lint`: 통과.
- `npm test`: 28개 통과, 별도 PostgreSQL 하니스 1개는 기본 실행에서 명시적 skip.
- 격리된 로컬 PostgreSQL에서 `RUN_POSTGRES_TEST=1 npx tsx --test tests/postgres.test.ts`: 7개 통과. 기존 거래흐름/RLS/승인 없는 실행 차단 및 새 식당 신청 확인.
- `npm run build`: 성공. 기존 object-store 동적 로컬 경로에 대한 tracing 경고가 있으며 설정에서 .data/.env/docs/tests 등을 제외한다. standalone 실제 비밀환경파일/.data 경로가 포함되지 않은 것을 확인했다.
- `npm run test:e2e`: 실제 standalone + Chromium, 공개10경로, 데스크톱1440px/모바일390px, 추가360px의 홈/서비스/요금/사례/FAQ/신청에서 전체 페이지 가로 넘침 없음.
- 새 폼 필수 항목만/담당자 생략/‘잘 모르겠음’/접수 저장/관리자에서 식별정보 표시 확인.
- 기존 로그인·익명접근 차단·진단 저장·보고서·비공개 PDF 다운로드·JavaScript 오류0 확인.
- 기존 SQLite 트랜잭션·조직 분리·동의·알림 중복 방지·비공개파일 테스트 통과. 새 폼 동의버전·중복/다른 지역 구분·구형 요청 호환성 테스트 추가.
- 실제 고객·운영 DB·메일 계정에는 테스트를 보내지 않았다. 브라우저 검증은 임시DB/로컬파일과 미발송 환경을 사용했다.

## 확인하지 않은 것과 운영 전 확인

이번 브랜치의 Render 실제 배포/운영 Supabase/Resend 발송/실고객 승인·플랫폼 작업·실결제·효과는 확인하지 않았다. 기존 운영 연결 성공은 사용자 확인 이력이며 이번 변경을 운영 확인한 것으로 확대하지 않는다.
추후 운영 적용 시 기존 운영 환경변수를 유지하고 (본문/표시명 등) 메일 발신자 이름도 한칸데이터인지 확인한다. 이번에 계정설정은 바꾸지 않았다.
가격·작업시간·고객 수요·권한별 대행 가능·시범 모집 조건·법률/세무/취소환불·플랫폼 심사시간은 별도 검증이 필요하다.
초기 무료2곳은 검토 중이며 공개 모집/확정 슬롯/날짜/할인율을 만들지 않았다.

## 검토용 실행

기존 Node24/Chromium 환경에서 `npm run build` 후 `APP_HOST=127.0.0.1 PORT=3140 npm start`.
접수 등 변경 확인에는 운영 DATABASE_URL/메일키를 제거하고 격리 DB/로컬 저장 경로를 지정한다.
운영 환경을 그대로 복사해 테스트하지 않는다. 검토 완료 후 운영 반영은 별도 지시로 진행한다.
