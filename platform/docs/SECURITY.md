# 보안·신뢰성·복구

## 적용
- Zod 입력검증, 입력 크기 제한, 별도 동의·honeypot, 영속 rate limit과 중복 고유키.
- 관리 API의 서버 측 세션·역할·org_id 확인. 다른 조직의 ID는404. customer 운영 API 차단.
- scrypt 비밀번호, 토큰 원문을 DB에 저장하지 않는8시간세션, HttpOnly/SameSite 쿠키와 운영Secure.
- 일반POST/PATCH의 Origin검사. `APP_URL`은 실제 HTTPS origin과 일치시킨다. 원격IP 헤더는 기본 신뢰하지 않는다. 프록시가 해당 헤더를 정리하는 배포에서만 TRUST_PROXY_HEADERS=true.
- PostgreSQL RLS·anon/authenticated 테이블 권한 차단. 비밀은 서버전용 환경변수.
- 불변 활동 이력, 변경별 고객권한·승인·철회·작업증빙. 외부 API는 미연결 실패 처리.
- 비공개 파일명은 난수, 조직별 디렉터리, 모든 다운로드 재인증. 파일은1MB이며 외부 공개 미리보기가 아니다.
- HTML보고서의 모든 고객문자열 이스케이프. 신뢰할 수 없는 외부URL을 PDF브라우저에서 불러오지 않음.
- 제공자 접수/실패/결과불명을 구분. 일일10회 제한과 idempotency key. 비밀·고객원문을 웹서버 오류로그에 출력하지 않음.
- `.data`, `.env*`를 Git/Docker context/standalone tracing에서 제외.

## 남은 운영 책임
이 MVP는 독립된 전문 침투시험이나 법적 적합성 인증을 받은 제품이 아니다. 공개 전에 실제 인프라에서 쿠키·HTTPS·접근권한·백업·계정 해지·동의문안·정산요건을 확인한다. 현재첨부는형식/크기검사만하며안티바이러스검사는없다. 서버 관리자도구와 DB 소유자는 높은권한을가진다.

## 백업
SQLite 운영은 단일 인스턴스·지속 볼륨을 쓴다. 실행 중 파일만 복사하지 말고 SQLite backup API 또는 점검시간에 DB/WAL 일관성을 확보한다. PostgreSQL은 관리형백업 또는 보호된 pg_dump를 사용한다. 비공개 파일 볼륨과 DB를 함께 백업하고 암호화·권한·보관기한을 적용한다. 복구 후 파일과 레코드의 연결 및 사용자 세션 만료를 확인한다. 과거백업에도고객정보가남을수있다.

## 장애 복구
PDF FAILED는환경수정후worker에서최대3회처리한다. PROCESSING이남은경우같은worker가실행중인지먼저확인하고운영자가재처리를결정한다. 외부메일 SENDING/UNKNOWN은SMTP/API제공자내역을확인한다. 자동으로되돌려중복발송하지않는다. 제공자키유출시회전하고,사용자비밀번호변경으로기존세션을폐기한다.
